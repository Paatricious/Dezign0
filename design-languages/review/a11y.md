# Accessibility review

How to run the accessibility pass of a design review. The rules a design must
meet live in `design-os/craft/accessibility.md`; this file is the reviewer's
procedure and the exact boundary of what the tool can prove.

Working target: **WCAG 2.2 AA**. The tool implements a heuristic subset. A clean
`--a11y` run is a floor, not a certificate.

---

## 1. Run the automated pass

```bash
node .design-os/tools/measure-artifact.mjs design/<slug>/artifact.html \
  --viewports=1440x900,1024x900,768x900,390x844,375x812,360x800,145x188 \
  --a11y --strict \
  --shots=design/<slug>/review/<YYYY-MM-DD>/shots
```

Useful variations:

```bash
# structured findings for a report or a script
node .design-os/tools/measure-artifact.mjs design/<slug>/artifact.html --a11y --json

# focus the pass on the widget cell only
node .design-os/tools/measure-artifact.mjs design/<slug>/artifact.html --viewports=145x188 --a11y
```

Semantics you must not misstate:

- The checks run at **every** viewport in the matrix. One clean width does not
  clear another; a control can lose its name only in a compact breakpoint.
- Findings are computed on every run, but `--a11y` controls **printing and
  blocking**. Without `--a11y` the JSON still contains `a11yCount`/`a11y`, the
  human output omits them, and `--strict` does not fail on them.
- With `--a11y --strict`, any finding makes `blocking: true` and exits 1.
  Without `--strict`, findings are reported and exit stays 0.
- Each viewport reports the total `a11yCount` and at most **12** findings in
  `a11y`. A count above 12 means the printed list is truncated; use `--json` and
  fix by category, not by scrolling.
- Findings are per instance, not deduplicated: the same bad control repeated ten
  times counts ten.

## 2. What the tool actually checks

Seven checks, keyed by `kind` in the output:

| `kind` | Fires when | Detail shown |
|---|---|---|
| `img-alt` | An `<img>` has no `alt` **attribute** at all. `alt=""` passes (decorative). | `<img src="…">` |
| `control-name` | A `button`, `a[href]`, `input` (not hidden, not submit), `select` or `textarea` has no accessible name from `aria-label`, `title` or text content. `placeholder` counts here. | `<tag>` |
| `input-label` | An `input` (not submit/button) has no `<label for>` matching its `id`, no ancestor `<label>`, and no `aria-label`. `placeholder` does **not** satisfy this check. | `<input id="…">` |
| `heading-h1` | Zero `<h1>`, or more than one. | `no h1` / `N h1 elements` |
| `heading-order` | A heading skips a level (e.g. `h2` followed by `h4`). | `H4 after h2` |
| `landmark-main` | No `<main>` or `[role="main"]`. | `no main landmark` |
| `tabindex-positive` | A `tabindex` value greater than 0. | element tag |

Controls inside `[inert]` subtrees are skipped (state boards mark static mocks
`inert`; that is intentional, not an exemption for the live prototype).

## 3. What the tool does not check

These are manual items. Each one is either performed and recorded, or listed as
`not reviewed` in the report.

- **Keyboard operability and focus order.** Whether Tab reaches everything, in
  order, and whether Enter/Space activate it.
- **Focus visibility and appearance** (2.4.7, 2.4.11, 2.4.13). The tool counts
  focusable controls; it never focuses one.
- **Non-text contrast** (1.4.11): input boundaries, toggle states, icon glyphs,
  chart series, focus rings. The rendered contrast pass measures **text only**,
  and does not see background images or gradients.
- **Colour is not the only signal** (1.4.1): error/status/selection conveyed by
  colour alone. Requires looking at the state screenshots.
- **Screen-reader output** (name/role/value, live announcements, table semantics,
  `aria-expanded`/`aria-current` correctness).
- **Reflow and zoom** (1.4.10, 1.4.4): 200% and 400% zoom, 320px reflow without
  two-dimensional scrolling.
- **Text spacing** (1.4.12) overrides: line height 1.5, letter spacing 0.12em,
  word spacing 0.16em, paragraph spacing 2em — no clipped content.
- **Target size** (2.5.8: 24×24 CSS px) and spacing between targets.
- **Dragging alternatives** (2.5.7) and **pointer gestures** (2.5.1).
- **Timing, pause and auto-advance** (2.2.1, 2.2.2).
- **Motion and flashing** (2.3.1, 2.3.3) and `prefers-reduced-motion` behaviour.
- **Forced-colors / high-contrast mode** and print styles.
- **Form error association** (3.3.1, 3.3.3): is the message programmatically tied
  to the field, and does focus move to the first error?
- **Consistent help** (3.2.6) and **accessible authentication** (3.3.8): the two
  2.2 additions most often missed.
- **Content on hover/focus** (1.4.13): dismissible, hoverable, persistent.

## 4. Manual passes

Do these in the browser, in this order, on the same revision as the automated
run. Record the outcome of each as `pass`, `fail (P0/P1)`, or `not reviewed`.

### 4.1 Keyboard only (10 minutes)

1. Click the address bar, then Tab through the artifact. Every visible control
   must receive focus, in visual order.
2. Watch the indicator at every stop: visible, not clipped, ≥3:1 against both
   the control and its surroundings.
3. Operate each control with Enter/Space. A dead control is a P0.
4. Open and close every overlay: focus trapped while open, Escape closes, focus
   returns to the invoking control.
5. Submit a form with errors: focus moves to the first error, and the error text
   is reachable from the field.

### 4.2 Zoom and reflow (5 minutes)

1. 200% zoom: no content lost, no overlap, no horizontal scroll.
2. 400% (or a 320 CSS px viewport): content reflows into one column.
3. Re-run the render matrix at 320×800 for the same artifact if the brief
   claims support below 360.

### 4.3 Reduced motion and forced colors (5 minutes)

1. Emulate `prefers-reduced-motion: reduce` and confirm translate/scale/rotate/
   parallax are gone while opacity/colour changes remain.
2. Emulate forced-colors and confirm boundaries, states and focus remain
   distinguishable without relying on the brand palette.

### 4.4 Screen-reader spot check (10 minutes)

Not a full audit. Check, in a real screen reader if available: the landmark
list, the heading tree, the name of every interactive control, one form error,
and one async status message. If no screen reader is available, write
`not reviewed — no screen reader` and do not imply the output is correct.

### 4.5 Targets and non-text contrast (5 minutes)

1. Measure the smallest interactive target. Below 24×24 CSS px is a 2.5.8
   failure unless an exception applies (inline link in a sentence, spacing
   exception, essential).
2. Measure boundaries and icons at 3:1 against the adjacent surface; measure the
   focus ring at 3:1 against both control and background.

## 5. Severity mapping

Use the kit's P0/P1/P2 so the a11y findings sort with the visual ones.

| Severity | Examples |
|---|---|
| **P0** | A control unreachable by keyboard; a primary action with no accessible name; body text below 4.5:1; an input with no programmatic label; focus invisible anywhere in the primary flow; content lost at 200% zoom |
| **P1** | Informative image without alt; no `<main>`; heading order skips; positive `tabindex`; status changes not announced; error not associated with its field; target under 24×24 in a touch product; colour-only error state |
| **P2** | Redundant `title` duplicating `aria-label`; decorative image with a verbose alt; inconsistent naming between a button and its confirmation |

Contrast failures on text the user must read are P0. Contrast on decorative or
non-essential text is reported as P1/P2 with its measured ratio — never silently
dropped.

## 6. Known false positives

State these instead of "fixing" them:

- `aria-labelledby` is not consulted, so a control named only that way can fail
  `control-name` or `input-label`. Verify the name in the accessibility tree
  before changing markup.
- Hidden or zero-size `<img>` elements (tracking pixels, `display:none` art) are
  still checked for `alt`.
- `title` satisfies `control-name`, which is technically weak but valid; flag it
  as P2 rather than a failure.
- An `alt=""` image is treated as decorative. If it conveys meaning, the failure
  is the empty alt, and the tool will not catch it.
- A heading inside a shadow root or an iframe is not seen. Neither is a control
  rendered by a canvas.

## 7. Evidence format

One row per finding, in the report packet:

| id | check | viewport | evidence | severity | fix |
|---|---|---|---|---|---|
| A11Y-01 | `input-label` | `145x188` | `<input id="qty">` at top of cell; no label node in DOM | P0 | Add a visible `<label for="qty">Qty</label>`; verify at all seven viewports |
| A11Y-02 | `tabindex-positive` | `1440x900` | `tabindex="2"` on the chart legend button | P1 | Remove the attribute; fix DOM order instead |

Also record, once per review:

- the exact command (including `--a11y` and the viewport string);
- browser build and Playwright availability;
- counts per viewport (`a11y=N` for each label);
- the manual passes performed and the ones skipped, with reasons;
- whether the artifact was modified (default: no).

A clean run with `a11y=0` at every viewport proves seven heuristics passed. The
report must not upgrade that into "accessible".
